Production Parity

"내 컴퓨터에서는 되는데?"를 없애는 원칙.

개발 환경에서 H2를 쓰면서 프로덕션에서 PostgreSQL을 쓰면, SQL 방언 차이로 예상치 못한 버그가 발생한다.
테스트도 프로덕션과 같은 DB를 쓰면 이 문제가 사라진다.

Test Isolation

각 테스트가 독립적으로 실행 가능해야 한다.

테스트 A가 만든 데이터가 테스트 B에 영향을 주면 안 된다. 현재 @DirtiesContext로 해결하고 있지만, DB 초기화로 더 효율적으로 격리할 수 있다.

Idempotency (멱등성)

몇 번을 실행해도 같은 결과가 나와야 한다.

테스트를 10번 돌려도 10번 다 통과해야 한다. 이를 위해 매 시나리오마다 DB를 깨끗하게 초기화한다.

BDD (Behavior-Driven Development)

비즈니스 언어로 테스트를 작성하는 방법론.

"선물하면 재고가 감소한다"를 코드가 아닌 자연어(한글)로 표현하여 개발자가 아닌 사람도 테스트를 읽고 이해할 수 있다.

수량만큼 재고가 줄어든다

@Nested
@DisplayName("재고가 충분할 때")
class WhenStockIsSufficient {

    @Test
    @DisplayName("수량만큼 재고가 줄어든다")
    void decreasesQuantity() {
        // given
        Option option = createOption(10);
        // when
        option.decrease(3);
        // then
        assertThat(option.getQuantity())
            .isEqualTo(7);
    }
}

    조건 재고가 10개인 옵션이 있다

    그러면 에러가 발생해야 한다

왼쪽은 개발자만 이해할 수 있고, 오른쪽은 누구나 이해할 수 있다

Given-When-Then 의미 매핑

Given (조건) = 사전 조건 설정

테스트가 시작되기 전 세상의 상태를 정의한다.
"재고가 10개인 옵션이 있다" = DB에 옵션 데이터를 생성하는 것
Java 코드의 // given 섹션과 동일

When (만일) = 행위 실행

테스트 대상 행위(Action)를 실행한다.
"3개를 선물한다" = POST /api/gifts API 호출
Java 코드의 // when 섹션과 동일

Then (그러면) = 결과 검증

행위의 결과가 기대와 일치하는지 확인한다.
"재고가 7개여야 한다" = assertThat().isEqualTo(7)
Java 코드의 // then 섹션과 동일

PostgreSQL + Docker Compose

프로덕션과 동일한 DB로 테스트하고,
Docker Compose로 환경을 자동화한다

왜 H2 대신 PostgreSQL인가?

H2 (현재) 문제점 
-- H2에서는 통과하지만...
SELECT * FROM product
WHERE name ILIKE '%선물%';
       ^^^^^ PostgreSQL 전용!

-- H2의 MySQL 호환 모드도
-- PostgreSQL과 100% 동일하지 않다

문제:
  - SQL 방언 차이
  - 트랜잭션 동작 차이
  - 타입 시스템 차이
  - 제약조건 검증 차이
➔
PostgreSQL (전환 후) 장점 
-- 프로덕션과 동일한 SQL!
SELECT * FROM product
WHERE name ILIKE '%선물%';
       ^^^^^ 동일하게 동작!

-- Docker로 누구나 쉽게 실행
-- 설치 필요 없음 (컨테이너)

장점:
  + Production Parity 달성
  + 실제 DB로 통합 테스트
  + 환경 차이 버그 제거
  + 누구나 동일한 환경

Docker Compose: 한 줄로 환경 구축

docker-compose.yml 구조 이해 YAML 
services:                       # 어떤 컨테이너를 띄울 것인가?
  postgres:                     # 서비스 이름 (= hostname)
    image: postgres:16          # 어떤 이미지를 쓸 것인가?
    ports:
      - "5432:5432"             # Host:Container 포트 매핑
    environment:                  # 환경변수 = DB 설정
      POSTGRES_DB: gift_test
      POSTGRES_USER: test
      POSTGRES_PASSWORD: test
    healthcheck:                  # 준비됐는지 어떻게 확인?
      test: ["CMD-SHELL", "pg_isready"]
      interval: 5s              # 5초마다 체크
      retries: 5                # 5번까지 재시도
    volumes:                      # 데이터 저장소
      - pgdata:/var/lib/postgresql/data

volumes:                         # 볼륨 정의
  pgdata:                        # 컨테이너 삭제해도 데이터 유지

Health Check & Gradle 자동화

Health Check가 왜 필요한가?

docker compose up 명령이 끝나도
PostgreSQL이 아직 준비 안 됐을 수 있다.

Health Check = "DB야, 진짜 준비됐어?"
pg_isready 명령이 OK를 반환할 때까지 기다린다.

이것 없이 테스트를 시작하면
Connection refused 에러가 난다.

Gradle Task로 자동화하기

Gradle Exec Task로 쉘 명령을 실행할 수 있다.

doFirst = "테스트 전에 DB 띄워!"
finalizedBy = "테스트 후에 DB 내려!"
(테스트가 실패해도 반드시 실행)

이렇게 하면 ./gradlew cucumberTest 한 줄로
DB 시작 → 테스트 → DB 정리가 자동으로 된다.

테스트 격리: DB 초기화

시나리오마다 DB를 깨끗하게 만들어야 한다.

방법: Cucumber @Before hook에서
TRUNCATE TABLE로 모든 테이블을 비운다.

현재의 @DirtiesContext보다
훨씬 빠르다 (Spring 컨텍스트 재시작 없이).

H2 vs PostgreSQL 테스트 분리

단위 테스트(OptionTest)는 H2 그대로 유지.
인수 테스트(Cucumber)만 PostgreSQL 사용.

분리 방법:
- ./gradlew test = H2 단위 테스트
- ./gradlew cucumberTest = PostgreSQL

Gradle에 별도 태스크를 만들면 된다.

Phase 2: 검색해봐야 할 키워드

docker-compose.yml services / volumes / ports healthcheck: pg_isready @ActiveProfiles("cucumber") application-cucumber.properties Gradle Exec task doFirst / finalizedBy TRUNCATE TABLE spring.datasource.url (JDBC) depends_on: condition: service_healthy
테스트 코드는 어디서 실행되는가?
Host (내 컴퓨터)에서 실행. PostgreSQL만 Docker 컨테이너 안. 그래서 localhost:5432로 접근한다.
테스트 실패해도 DB가 정리되는가?
finalizedBy를 쓰면 테스트가 실패해도 docker compose down이 반드시 실행된다.

Phase 2: 학습 절차

1

docker-compose.yml 작성

PostgreSQL 서비스 정의, 포트 매핑(5432:5432), healthcheck 설정, 환경변수(DB명, 사용자, 비밀번호) 세팅

2

application-cucumber.properties 생성

PostgreSQL JDBC URL, 사용자 정보, JPA 방언 설정. spring.jpa.hibernate.ddl-auto=create-drop 으로 스키마 자동 생성

3

build.gradle에 PostgreSQL 드라이버 추가

runtimeOnly 'org.postgresql:postgresql' 의존성 추가. cucumberTest 태스크 정의

4

Gradle 자동화 태스크 구현

dockerUp (compose up -d --wait), cucumberTest (실제 테스트), dockerDown (compose down). finalizedBy로 연결

5

DB 초기화 로직 추가

@Before hook에서 JdbcTemplate으로 TRUNCATE 실행. @ActiveProfiles("cucumber") 적용 확인

03

Application 컨테이너화

앱까지 Docker로 실행하여
프로덕션과 완전히 동일한 E2E 테스트

Multi-stage Build: 왜 필요한가?

Stage 1: Builder

  • JDK 21 (빌드 도구 포함)
  • 소스 코드 복사
  • ./gradlew build 실행
  • JAR 파일 생성
  • 테스트, 컴파일러 등 포함
~800MB (무거움)
➔

Stage 2: Runtime

  • JRE 21 Alpine (실행만 가능)
  • JAR 파일만 복사
  • java -jar app.jar 실행
  • 빌드 도구 없음
  • 경량 Linux 기반
~150MB (가벼움!)

핵심: Builder에서 만든 JAR 파일만 Runtime으로 복사한다.
COPY --from=builder 명령이 이 "복사" 역할을 한다.
결과: 프로덕션 이미지에는 불필요한 빌드 도구가 없다

핵심 개념: Docker 네트워크

Host (내 컴퓨터)

테스트 코드
./gradlew cucumberTest
→ HTTP →
localhost:28080
Docker Network

→ JDBC →
postgres:5432

DB cleanup: localhost:5432

Host에서 접근: localhost:28080 (포트 매핑 28080 → 8080)
Container 간 접근: postgres:5432 (서비스 이름 = hostname)
테스트 DB 정리: localhost:5432 (Host에서 직접 DB 접근)

왜 webEnvironment = NONE인가?

Phase 2 vs Phase 3: 테스트 방식의 차이

Phase 2: @SpringBootTest(RANDOM_PORT) - 테스트가 직접 Spring Boot 서버를 띄움
Phase 3: @SpringBootTest(NONE) - Docker가 이미 서버를 띄워놓았으므로, 테스트는 HTTP 클라이언트만 되면 됨

NONE을 쓰는 이유

앱이 Docker 컨테이너 안에서 이미 실행 중이다.

테스트 코드에서 또 서버를 띄우면
서버가 2개가 되어 혼란스럽다.

테스트 코드는 순수하게
"HTTP 요청 보내고 응답 확인"만 하면 된다.

JdbcTemplate이 필요한 이유

앱은 Docker 안에서 돌지만,
DB 초기화는 테스트 코드에서 해야 한다.

테스트 코드가 localhost:5432로
직접 DB에 접근하여 TRUNCATE 하려면
JdbcTemplate이 필요하다.

Phase 3: 검색해봐야 할 키워드

Multi-stage build (FROM ... AS builder) COPY --from=builder eclipse-temurin:21-jre-alpine depends_on: condition: service_healthy SPRING_DATASOURCE_URL (환경변수) Port mapping 28080:8080 webEnvironment = NONE .dockerignore Docker network (서비스명 = hostname) JdbcTemplate (DB cleanup)
컨테이너 안에서 postgres:5432인 이유는?
Docker Compose가 같은 네트워크에 컨테이너를 배치하고, 서비스 이름을 DNS로 등록한다. "postgres"가 IP 대신 사용됨.
.dockerignore는 왜 필요한가?
.gradle, build, .git 등을 제외해서 Docker 빌드 컨텍스트를 줄인다. 빌드 속도가 크게 향상됨.

Phase 3: 학습 절차

1

Dockerfile 작성 (Multi-stage)

Stage 1: gradle:jdk21로 빌드 & JAR 생성. Stage 2: eclipse-temurin:21-jre-alpine에 JAR만 복사하여 실행

2

docker-compose.yml에 앱 서비스 추가

app 서비스 정의, depends_on으로 postgres 의존, 환경변수로 DB URL 주입(postgres:5432), 포트 28080:8080 매핑

3

.dockerignore 작성

.gradle, build, .git, .idea 등 불필요한 파일 제외하여 빌드 컨텍스트 최적화

4

Gradle 태스크 추가 (dockerBuild, dockerUp, dockerDown)

docker compose build, up -d --wait, down 명령을 Gradle Exec 태스크로 감싸기

5

Cucumber 테스트를 Docker 앱에 연결

webEnvironment=NONE으로 변경. base URL을 localhost:28080으로 설정. JdbcTemplate으로 DB 초기화 유지

막혔을 때: 트러블슈팅 키워드

Connection refused

DB가 아직 준비 안 됐을 가능성이 높다.
docker ps로 컨테이너 상태 확인.
healthcheck가 제대로 설정됐는지 확인.

Port already in use

이전 실행이 정리 안 된 것.
docker compose down으로 정리하거나
docker ps로 실행 중인 컨테이너 확인.

Step undefined

Feature 파일의 텍스트와
Step Definition의 어노테이션 텍스트가
정확히 일치하지 않을 때 발생.

Docker 빌드 느림

.dockerignore 확인.
build/, .gradle/ 이 포함되지 않으면
수 GB의 파일이 복사되어 느려진다.

디버깅 명령어: docker ps | docker logs [컨테이너] | docker exec -it [컨테이너] bash | docker system prune

전체 요약: 3단계 핵심 정리

Phase 1: Cucumber BDD

  • Gherkin = 사람이 읽는 명세서
  • Given/When/Then = 조건/만일/그러면
  • Step Definitions = 명세 → 코드 연결
  • @ScenarioScope = 시나리오별 격리
  • 핵심: 비개발자도 읽을 수 있는가?

Phase 2: PostgreSQL

  • H2 → PostgreSQL = Production Parity
  • Docker Compose = 환경 자동화
  • Health Check = DB 준비 대기
  • Spring Profile = 환경별 설정 분리
  • 핵심: 한 줄로 환경이 준비되는가?

Phase 3: 컨테이너화

  • Multi-stage = 빌드/실행 분리
  • 서비스명 = Docker 내 hostname
  • webEnvironment=NONE 사용
  • JdbcTemplate으로 DB 초기화
  • 핵심: 프로덕션과 동일한가?
