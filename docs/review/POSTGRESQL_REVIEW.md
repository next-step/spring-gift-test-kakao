# PostgreSQL + Docker Compose 통합 코드 리뷰

## 총평

PostgreSQL + Docker Compose 통합이 핵심 흐름은 올바르게 구성되어 있습니다. Docker Compose healthcheck, Spring Profile 분리, Gradle 태스크 분리(`test` vs `cucumberTest`), PostgreSQL용 cleanup SQL 전환 모두 동작하며, 8개 Cucumber 시나리오가 PostgreSQL에서 100% 통과합니다. 다만 **운영 안정성과 팀 협업 관점**에서 몇 가지 중요한 개선 포인트가 있습니다.

## 발견된 문제점

### 🔴 치명적: `finalizedBy 'dockerComposeDown'`이 주석 처리되어 있다

**파일:** `build.gradle:61`

```gradle
tasks.register('cucumberTest', Test) {
    // ...
    dependsOn 'dockerComposeUp'
//  finalizedBy 'dockerComposeDown'
}
```

**문제:** 테스트 종료 후 PostgreSQL 컨테이너가 계속 실행 상태로 남습니다. 이로 인해:

1. **포트 충돌**: 다른 프로젝트나 다음 실행 시 5432 포트가 이미 점유되어 충돌 가능
2. **리소스 누수**: 개발 머신에서 불필요한 Docker 컨테이너가 계속 자원을 소비
3. **CI/CD 환경에서 치명적**: CI 러너에서 컨테이너가 정리되지 않으면 후속 빌드에 영향

개발 중 디버깅 편의를 위해 주석 처리한 것으로 보이지만, **최종 제출 시에는 반드시 활성화**해야 합니다.

**개선된 코드:**

```gradle
tasks.register('cucumberTest', Test) {
    useJUnitPlatform()
    testClassesDirs = sourceSets.test.output.classesDirs
    classpath = sourceSets.test.runtimeClasspath
    include '**/CucumberTest.class'
    dependsOn 'dockerComposeUp'
    finalizedBy 'dockerComposeDown'
}
```

> `finalizedBy`는 테스트가 실패해도 반드시 실행됩니다. 즉, 테스트 성공/실패 관계없이 컨테이너가 정리됩니다. 이것이 요구사항에서 "테스트 실패 시에도 DB가 정리되는가?"라고 물은 이유입니다.

### 🟡 경고: `GenerationType.IDENTITY`와 PostgreSQL의 TRUNCATE + RESTART IDENTITY 호환성 이해

**파일:** 모든 엔티티 (`Category.java`, `Product.java`, `Option.java`, `Member.java`, `Wish.java`)

```java
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

**현재 상태:** `ddl-auto=create`이므로 Hibernate가 PostgreSQL에서 `GENERATED BY DEFAULT AS IDENTITY` 컬럼을 생성합니다. `TRUNCATE ... RESTART IDENTITY CASCADE`가 이 시퀀스를 리셋하므로 **현재는 정상 동작**합니다.

**잠재적 문제:** `ScenarioContext`의 `nextOptionId()`, `nextMemberId()`로 직접 ID를 지정하여 INSERT하는 Step Definition이 있습니다(`GiftStepDefinitions.java:23-27`). PostgreSQL의 `GENERATED BY DEFAULT AS IDENTITY`는 명시적 ID를 허용하지만, **IDENTITY 시퀀스 값은 증가하지 않습니다**. 즉:

```
수동 INSERT (id=1) → 시퀀스 값은 여전히 1
수동 INSERT (id=2) → 시퀀스 값은 여전히 1
API로 INSERT    → 시퀀스가 1을 할당 → id=1 중복 → UNIQUE 위반!
```

현재 테스트에서는 카테고리/상품은 API로 생성하고 옵션/회원은 JdbcTemplate으로만 생성하여 섞이지 않기 때문에 문제가 발생하지 않습니다. 하지만 향후 시나리오에서 API 생성과 JdbcTemplate 생성을 혼용하면 깨질 수 있습니다.

**개선 방향:** 1단계 리뷰에서도 언급했지만, INSERT 후 실제 생성된 ID를 받아오는 방식이 더 안전합니다.

```java
// PostgreSQL에서 INSERT 후 ID 받기
Long id = jdbcTemplate.queryForObject(
    "INSERT INTO option (name, quantity, product_id) VALUES (?, ?, ?) RETURNING id",
    Long.class, optionName, quantity, productId
);
scenarioContext.putOptionId(optionName, id);
```

### 🟡 경고: `docker-compose` 명령어가 레거시 형식이다

**파일:** `build.gradle:48-49, 52-53`

```gradle
tasks.register('dockerComposeUp', Exec) {
    commandLine 'docker-compose', 'up', '-d', '--wait'
}
tasks.register('dockerComposeDown', Exec) {
    commandLine 'docker-compose', 'down'
}
```

**문제:** Docker Compose V2부터 공식 명령어는 `docker compose` (하이픈 없음)입니다. `docker-compose` (하이픈 있음)는 V1 호환 래퍼로, 일부 환경에서는 설치되어 있지 않을 수 있습니다. 현재 머신에서는 V2(`Docker Compose version v5.0.2`)가 설치되어 있어 동작하지만, **다른 개발자의 환경에서는 실패할 수 있습니다.**

요구사항의 "다른 개발자도 동일한 명령으로 실행 가능한가?"에 직결됩니다.

**개선된 코드:**

```gradle
tasks.register('dockerComposeUp', Exec) {
    commandLine 'docker', 'compose', 'up', '-d', '--wait'
}

tasks.register('dockerComposeDown', Exec) {
    commandLine 'docker', 'compose', 'down'
}
```

### 🟡 경고: `docker-compose.yml`에 볼륨이 없어 데이터가 휘발성이다

**파일:** `docker-compose.yml`

```yaml
services:
  postgres:
    image: postgres:17
    ports:
      - "5432:5432"
    environment:
      POSTGRES_DB: gift_test
      POSTGRES_USER: gift
      POSTGRES_PASSWORD: gift1234
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U gift -d gift_test"]
      interval: 3s
      timeout: 3s
      retries: 5
```

**현재 상태:** `ddl-auto=create`이므로 매번 스키마가 새로 생성되고, 볼륨이 없으므로 `docker compose down`하면 데이터가 완전히 삭제됩니다.

**이것은 테스트 환경에서는 오히려 장점입니다** — 매 테스트 실행이 깨끗한 상태에서 시작됩니다. 의도적인 선택이라면 좋습니다.

다만 향후 개발 환경용으로도 사용할 계획이라면 볼륨 추가를 고려할 수 있습니다:

```yaml
services:
  postgres:
    # ...
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:
```

### 🟡 경고: `ddl-auto=create`는 매번 테이블을 DROP + CREATE한다

**파일:** `application-cucumber.properties:6`

```properties
spring.jpa.hibernate.ddl-auto=create
```

**동작:** 애플리케이션 시작 시 기존 테이블을 모두 DROP하고 엔티티 기반으로 재생성합니다. `cucumberTest` 태스크에서는 Spring Boot가 한 번만 뜨고 8개 시나리오가 모두 실행되므로, **시나리오 간 스키마 리셋은 일어나지 않습니다**. cleanup은 `TRUNCATE`로 처리됩니다.

**잠재적 문제:**
- Production과 DDL 구조가 다를 수 있음 (Hibernate가 생성하는 DDL ≠ 실제 마이그레이션 DDL)
- 향후 Flyway/Liquibase 도입 시 충돌

현재 단계에서는 `create`가 가장 간단한 선택이며, Production Parity를 완전히 달성하려면 추후 마이그레이션 도구 도입을 고려하면 됩니다.

### 🟢 개선 권장: `cucumberTest` 실행 시 Gradle 에러 핸들링

**파일:** `build.gradle:47-53`

현재 `dockerComposeUp` 태스크가 실패하면(Docker 미설치, 포트 충돌 등) Gradle이 빌드 실패로 종료하긴 합니다. 하지만 **에러 메시지가 직관적이지 않을 수 있습니다.**

**개선 방향:** `doFirst`에서 Docker 사용 가능 여부를 먼저 체크하면 실패 원인 파악이 쉬워집니다.

```gradle
tasks.register('dockerComposeUp', Exec) {
    commandLine 'docker', 'compose', 'up', '-d', '--wait'
    doFirst {
        // Docker가 실행 중인지 확인
        exec {
            commandLine 'docker', 'info'
            standardOutput = new ByteArrayOutputStream()
            errorOutput = new ByteArrayOutputStream()
            ignoreExitValue = true
        }.assertNormalExitValue()
    }
}
```

### 🟢 개선 권장: H2 AcceptanceTest와 Cucumber PostgreSQL 테스트의 관계 명확화

현재 테스트 실행 분리:

| 태스크 | DB | 실행 대상 | 테스트 수 |
|---|---|---|---|
| `./gradlew test` | H2 | AcceptanceTest 3개 클래스 | 8 tests |
| `./gradlew cucumberTest` | PostgreSQL | CucumberTest (Cucumber 시나리오) | 8 tests |

이 분리 자체는 우수합니다. 기존 H2 기반 AcceptanceTest는 빠른 피드백 루프로, PostgreSQL Cucumber 테스트는 Production Parity 검증으로 역할이 나뉩니다.

**한 가지 주의점:** 두 테스트 셋이 **동일한 시나리오를 다른 DB에서 실행**하고 있습니다. 이는 의도적인 설계(H2 빠른 검증 + PostgreSQL 호환성 검증)라면 좋지만, 장기적으로는 유지보수 부담이 됩니다. 향후 방향성을 결정해두면 좋습니다:

- **옵션 A:** Cucumber 테스트로 통일하고 기존 AcceptanceTest는 제거
- **옵션 B:** AcceptanceTest는 단위 검증용, Cucumber는 통합 검증용으로 역할 분리
- **옵션 C:** 현재처럼 공존 유지 (단, 시나리오 추가 시 두 곳 모두 업데이트 필요)

## 추가 조언

### 1. Production Parity에 대해 생각해보기

이번 미션의 핵심 질문은 **"왜 H2 대신 PostgreSQL을 사용하는가?"**입니다. 답은 **Production Parity** — 프로덕션과 동일한 환경에서 테스트해야 "프로덕션에서만 발생하는 버그"를 사전에 잡을 수 있다는 원칙입니다.

실제로 H2와 PostgreSQL의 차이가 문제를 일으키는 예:
- H2의 `IDENTITY` vs PostgreSQL의 `GENERATED AS IDENTITY` (시퀀스 동작 차이)
- H2는 대소문자 구분 없음 vs PostgreSQL은 기본적으로 소문자
- `TRUNCATE` 문법 차이 (`RESTART IDENTITY CASCADE`는 PostgreSQL 전용)
- JSON 타입 지원 차이

이번 작업에서 `cleanup.sql`(H2)과 `cleanup-pg.sql`(PostgreSQL)을 분리한 것이 바로 이 차이를 보여줍니다.

### 2. Docker Compose `--wait` 플래그의 의미

```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U gift -d gift_test"]
  interval: 3s
  timeout: 3s
  retries: 5
```

`docker compose up -d --wait`는 healthcheck가 `healthy` 상태가 될 때까지 기다립니다. 이것이 없으면 PostgreSQL 컨테이너가 시작 중일 때 테스트가 연결을 시도하여 `Connection refused` 에러가 발생합니다. healthcheck + `--wait`의 조합은 **경쟁 조건(race condition)을 방지**하는 핵심 패턴입니다.

### 3. `.gitignore`에 Docker 관련 항목 확인

Docker volume 데이터나 `docker-compose.override.yml` 같은 로컬 설정 파일이 커밋되지 않도록 `.gitignore`를 확인하세요.

### 4. 보안: `docker-compose.yml`의 패스워드

```yaml
POSTGRES_PASSWORD: gift1234
```

테스트 환경용이므로 현재는 문제없지만, 이 파일이 프로덕션 설정과 혼동되지 않도록 주의하세요. 프로덕션에서는 환경변수나 시크릿 매니저를 사용해야 합니다.

## 생각해보면 좋을 점

1. **Testcontainers 대안**: Docker Compose 대신 [Testcontainers](https://testcontainers.com/)를 사용하면 Java 코드 내에서 컨테이너를 관리할 수 있습니다. Gradle 태스크로 Docker를 직접 제어하는 현재 방식과 비교했을 때 장단점이 무엇일까요?

3. **CI/CD에서의 Docker Compose**: GitHub Actions나 Jenkins에서 `docker compose`를 사용하려면 어떤 추가 설정이 필요할까요? DinD(Docker in Docker)나 서비스 컨테이너 방식과의 차이점은?

4. **포트 충돌 방지**: 현재 `5432:5432`로 고정 포트를 사용합니다. 로컬에 PostgreSQL이 이미 설치된 개발자는 포트 충돌이 발생합니다. 이를 해결하는 방법은?
